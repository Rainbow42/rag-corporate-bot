# Проектная работа 7 — QuantumForge RAG

## 1. Модели и инфраструктура

### Рассмотренные варианты

| Вариант | Качество и скорость | Стоимость | Эксплуатация | Приватность |
|---|---|---|---|---|
| Локальная LLM + SentenceTransformers + FAISS | Качество зависит от размера модели; стабильная задержка | Нет оплаты за запросы, но нужны локальные ресурсы | Нужно устанавливать и обновлять модель | Максимальная |
| OpenAI + OpenAI Embeddings + облачная БД | Высокое качество, быстрый старт | Оплата токенов, embeddings и БД | Минимальная локальная поддержка | Данные покидают контур |
| YandexGPT + облачные embeddings | Хорош для русского языка | Оплата API и хранения | Требует интеграции с облаком | Зависит от выбранного контура |
| OpenAI LLM + локальные embeddings + FAISS | Высокое качество генерации, быстрый локальный retrieval | Платим только за LLM | FAISS прост для одного экземпляра | В API уходит только найденный контекст |

Для учебного MVP выбран первый, полностью локальный вариант: Qwen2.5 3B через Ollama, SentenceTransformers и FAISS. Он не требует платного API и не передаёт документы внешнему провайдеру. Небольшая модель подходит для демонстрации на обычном компьютере; для production потребуется нагрузочное тестирование и, вероятно, более крупная модель на GPU.

### Эмбеддинги

`paraphrase-multilingual-MiniLM-L12-v2` выбрана вместо облачных embeddings: модель поддерживает русский язык, работает локально и не создаёт переменную стоимость повторной индексации. Размерность — 384. Облачные embeddings могут дать более высокое качество на сложных запросах, но требуют передачи текста провайдеру и оплаты каждого обновления.

### Векторная БД

FAISS быстрее внедрить для локального MVP: нет отдельного сервера и лицензионной стоимости, а `IndexFlatIP` даёт точный поиск по небольшому индексу. ChromaDB удобнее для серверного API, metadata-фильтров и нескольких клиентов, но добавляет эксплуатационный компонент. При росте до нескольких команд FAISS следует заменить на ChromaDB или управляемую векторную БД.

### Сервер

Для учебного MVP с Qwen2.5 3B достаточно 4–8 CPU, 8–16 GB RAM и 20 GB SSD; GPU не обязателен, но ускоряет генерацию. Индексация 18 000 коротких документов может выполняться отдельной задачей на 8 vCPU и 32 GB RAM. Для production-варианта с более крупной локальной LLM рекомендуется GPU с 16–24 GB VRAM.

## 2. База знаний

В качестве известного исходного мира использована вселенная Star Wars. `seed_knowledge_base.py` содержит 33 разные перефразированные сущности и словарь замен исходных названий на термины Nebula Forge; исходные страницы перечислены в `sources.json`. Три сущности исключаются для эксперимента с пробелами, поэтому итоговая индексируемая база содержит 30 уникальных тематических документов и один вредоносный fixture. Исходные названия хранятся только в `terms_map.json` и не попадают в индекс.

## 3. Векторный индекс

`rag_core.py` разбивает документы на чанки по 180 слов с overlap 30, сохраняя имя источника, заголовок, `chunk_id` и позиции слов. Модель SentenceTransformer создаёт нормализованные 384-мерные векторы. FAISS `IndexFlatIP` выполняет cosine-поиск через скалярное произведение. `build_index.py` сохраняет индекс, чанки и manifest с моделью, размерностью и хешами документов. Проверочная сборка 31 чанка заняла 28,9 секунды, размер FAISS-файла — 47 661 байт.

## 4. RAG и промптинг

Пайплайн использует один энкодер для индексации и вопроса, выбирает пять ближайших чанков, применяет порог релевантности, собирает контекст и вызывает локальную Qwen2.5 3B через OpenAI-совместимый API Ollama. System prompt содержит few-shot пример, запрещает выполнять инструкции из документов и требует объяснение через найденные факты и вывод. Интерфейсы: FastAPI и обязательный для тарифа «Про» Telegram-бот.

## 5. Демонстрация и защита

`knowledge_base/malicious.md` индексируется вместе с остальными файлами. Защита состоит из проверки пользовательского запроса, фильтрации retrieved-чанков, запрета в system prompt и post-check ответа. `PROTECTION_MODE=off` предназначен только для сравнения поведения в локальном эксперименте. Golden set содержит полезные запросы, отсутствующие темы и провоцирующий запрос с `swordfish`.

## 6. Ежедневное обновление

`update_index.py` сравнивает SHA-256 документов с manifest. Если изменений нет, индекс не перестраивается. При добавлении, изменении или удалении файлов небольшой FAISS-индекс полностью пересобирается — так корректно обрабатываются удаления. В JSONL-лог пишутся начало, окончание, длительность, число изменений, число чанков, размер индекса и ошибки. Контейнер `scheduler` запускает задачу ежедневно в 06:00.

## 7. Покрытие и качество

Из базы намеренно исключены Xarn Velgor, VoidCore и Synth Flux. `golden_questions.json` содержит семь известных и пять отсутствующих/опасных вопросов с ожидаемыми терминами и источниками. `evaluate.py` проверяет не только наличие ответа, но также ожидаемые факты и источники. Лог запросов содержит timestamp, факт retrieval, top score, длину ответа, источники, статус защиты и latency.

Ожидаемые пробелы — три исключённые сущности. Если известный вопрос не проходит проверку, нужно расширить соответствующий документ или откалибровать порог на отдельном validation-наборе. Нерелевантные источники анализируются по `sources` и `top_score`; часто запрашиваемые отсутствующие темы являются кандидатами на пополнение базы.

## Воспроизводимость

Команды полного запуска и проверки приведены в README. Рабочие индексы и логи генерируются заново и не хранятся в Git. Архитектурные диаграммы находятся в `docs/index_update.puml` и `docs/query_evaluation_sequence.puml`.
